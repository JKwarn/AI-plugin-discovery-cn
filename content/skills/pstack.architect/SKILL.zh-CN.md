# Architect：架构设计

先使用 not implemented 函数体和伪代码，勾勒类型、函数签名、类结构和模块边界。综合多个模型视角后，再依据选定的设计草图补全代码。

## 开始

开始前，先创建一个待办清单，每个阶段对应一项：

1. Ground（理解现状）
2. Sketch（绘制设计草图）
3. Agree（达成一致）
4. Implement（实施）
5. Scrap（废弃并重设计）

## 阶段 A：建立问题的真实上下文（Ground）

对新代码涉及的每个系统建立真实、准确的心智模型。针对相关子系统运行 **how** Skill。仅仅指出某个文件名不算完成上下文梳理；必须产出 **how** 规定的架构说明。

如果设计会重新定义所有权关系或分层，还应针对现有结构运行 **why** Skill，使其设计理由成为约束条件，而不是未经验证的猜测。

只有当工作确实是一个无需与周边系统集成的全新绿地项目（greenfield）时，才可以跳过阶段 A。

## 阶段 B：绘制设计草图（Sketch）

使用设计草图任务运行 **arena** Skill，并提供阶段 A 的上下文梳理产物。每个 runner 都使用 references/runner-prompt.md 作为提示词。

使用 pstack-models.mdc 规则中的 architect runners 配置行来选择 runner，替代 **arena** Skill 中的 arena runners 配置行。如果规则或该配置行不存在，则使用 claude-opus-5-5-xhigh 和 grok-4.7-xhigh-fast。别名和被拒绝的配置项，遵循 **arena** Skill 阶段 A 中的 runner 规则。

必须设计两次。即使第一个方案看起来已经足够，也至少要求在综合之前提出两个结构上明显不同的候选方案。这是将 **exhaust-the-design-space**（穷尽设计空间）原则 Skill 具体落实到设计过程中的做法。候选方案应当是整体结构不同的替代设计，而不是在同一结构中提出若干局部修补。

在综合之前，使用 references/design-red-flags.md 检查每个候选方案。假设下一位贡献者是一个只能看到自己打开文件的 Agent：它会复制最近的示例，并选择能够编译的最短路径。应优先选择这样的设计：即使只从单个文件观察，某项看似正确的修改，对整个仓库而言也仍然是正确的。

比较可行方案的接口深度。优先选择能够通过更小、更简单的公共接口隐藏更多复杂性的设计。丰富的接口可以通过集中能力而非将能力分散到多个层次，缩短调用链。

Arena 应返回一个综合后的设计包。其综合结论应填写在 rationale 的 “Synthesis decision”（综合决策）章节中。

## 阶段 C：达成一致（Agree，可选）

默认行为：直接依据综合后的设计进入实施阶段，不设置人工检查点。

只有当调用者明确提出要求时，才启用检查点，例如“/architect with checkpoint”“实施前停下来给我看”等。此时应展示综合后的设计，并暂停等待确认。

无论是否设置检查点，综合设计都可以作为独立提交先行交付，这对应 **foundational-thinking** 原则 Skill 中的 “scaffold first”（先搭骨架）模式。根据 **outcome-oriented-execution** 原则 Skill，在补全实现期间，有计划且范围明确的暂时性破坏是可以接受的。

如果希望在实施前对设计进行对抗性审查，可以针对综合后的草图运行 **interrogate** Skill。

如果用户（无论是在检查点中还是事后）对设计结构提出异议，应将其视为阶段 A 的新证据。重新梳理上下文，并在继续编写代码前重新运行阶段 B。

## 阶段 D：依据草图实施（Implement）

将 not implemented 函数体替换为代码，将伪代码替换为实际逻辑。综合后的设计草图就是实现契约。

任何偏离草图的情况都应被视为需要明确提出的信号，而不是可以默默消化的摩擦。如果某个函数需要草图中未预料到的参数，应先判断：是草图有误、遗漏了需求，还是实现超出了范围。

## 阶段 E：架构错误时废弃重来（Scrap）

如果实现过程持续产生设计草图无法消化的阻力，就应废弃草图。不要在错误的设计上不断叠加修补。遵循 **redesign-from-first-principles**（从第一性原理重新设计）和 **fix-root-causes**（修复根因）原则 Skill。

判断依据应当是反复出现的模式，而不是单个例子。典型信号包括：

- 在互不相关的代码中反复出现同一种变通方案。
- 多个互不相关的边界情况都需要特殊分支处理。
- 类型必须依赖逃生口（例如 any、类型转换，或实际上总会被赋值的可选字段）才能通过编译。
- 草图认为状态并不共享，调用者却本能地提出“需要加锁”。
- 调用者必须了解抽象内部规则才能正确使用它。
- 实施阶段 D 中出现两个或更多同类型的独立偏离。

应当运用判断力。少数边界情况并不能证明架构失败；有些问题本来就很复杂。数据本身复杂，不等于设计复杂。

废弃草图时：

1. 针对已经构建的内容重新运行 **how** Skill。
2. 按照 **redesign-from-first-principles**，将新约束视为从项目第一天起就存在的前提，重新设计。
3. 遵循 **subtract-before-you-add**（先减后加）原则 Skill：新草图在扩展之前，应先比旧草图更小、更精简。
4. 返回阶段 B，重新运行 arena。

## 输出

先写调用方如何使用，再从使用方式推导类型草图。

- 小型变更：一个文件，包含新类型和函数签名。
- 较大型变更：模块映射及类型定义。

设计理由（rationale）应与草图一同交付，格式遵循 references/rationale-template.md，并包含使用方式草图和综合决策。
